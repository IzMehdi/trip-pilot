# M3 — NVIDIA LLM agent and function calling

## Role

Act as Project Manager/Supervisor. Delegate NVIDIA client, tool definitions and QA to separate Pi agents only after defining the shared tool contract. Use the exact endpoint/model verified in M0.

## Objective

Build a backend-controlled AI agent that uses an NVIDIA-hosted model to decide when to call TripPilot tools, receives real provider results and produces a grounded trip-planning response.

## NVIDIA client

- Use the OpenAI-compatible SDK only if M0 verified compatibility for the chosen endpoint.
- Read base URL, API key and model ID from validated environment configuration.
- Never hardcode credentials or model identifiers in source code.
- Support configurable request timeout, bounded retries for safe transient errors and cancellation.
- Record model ID, request ID where available, latency and token usage where returned.
- Handle model refusal, malformed arguments, unsupported tool calls, rate limits and unavailable models.
- Do not silently switch to a non-NVIDIA provider.

## Tool architecture

Implement a typed tool registry. Suggested initial tools:

1. `search_flights`
   - Validated origin/destination, dates, passenger count, currency and optional filters.
2. `get_weather_forecast`
   - Coordinates or resolved destination and date range.
3. `search_places`
   - Destination, category/query, location bias and bounded result count.
4. `get_route`
   - Origin/destination place identifiers or coordinates and travel mode.
5. `get_place_details`
   - Provider place ID and explicitly allowed field selection, if needed.

The model may request a tool, but backend code must validate arguments, enforce permissions and limits, call the service, validate the result and return a compact result to the model.

## Agent execution loop

- Send system instructions, user request and available tool schemas to the model.
- Parse the model response.
- If it requests tools, validate each tool name and arguments against the registry.
- Execute tools with bounded concurrency and per-tool timeouts.
- Return tool results to the model using the provider's documented tool-result format.
- Continue until a final answer is produced or a strict maximum tool-round/total-call budget is reached.
- Reject unknown tools and malformed arguments.
- Prevent repeated identical calls and excessive searches.
- Ensure tool output is treated as untrusted data, not instructions.
- Keep a trace of tool name, sanitized arguments, duration, status and source; never log secrets.
- Never fabricate a successful tool result when an API fails.

## Grounding rules in the system prompt

- Use only tool-returned data for flight offers, weather, places and route estimates.
- Clearly distinguish forecast from climate averages or historical conditions.
- If data is missing or outside provider horizon, say so.
- State currency and retrieval time for flight prices.
- Do not imply that a flight price is guaranteed or bookable until a provider confirms it.
- Do not make bookings or payments.
- Ask the user for missing essential trip details rather than guessing.

## Tests

- Unit-test tool schemas and invalid arguments.
- Mock the NVIDIA client and provider adapters for deterministic agent-loop tests.
- Test tool success, provider failure, malformed model arguments, unknown tool, repeated calls, maximum rounds and cancellation.
- Add an opt-in NVIDIA smoke test that requires explicit environment configuration.
- Verify tool calling with the actual chosen model; do not rely solely on mocks.

## Delegation

- AI agent: NVIDIA client and agent loop.
- Tools agent: registry, schemas, executor and safety limits.
- QA agent: adversarial tool-call tests and provider grounding review.
- Supervisor: shared interfaces, prompt review, integration and real endpoint verification.

## Acceptance criteria

- [ ] Actual NVIDIA endpoint/model works with the application.
- [ ] Actual model function/tool calling is verified.
- [ ] Tool schemas are validated server-side.
- [ ] Agent can call at least one real provider tool end-to-end.
- [ ] Tool execution is bounded and observable.
- [ ] Provider failures are surfaced honestly.
- [ ] No secrets or raw sensitive payloads enter logs or model context unnecessarily.
- [ ] Deterministic tests pass.
- [ ] Human approves before M4.

## Out of scope

No frontend streaming implementation, booking actions or autonomous background trip execution.
