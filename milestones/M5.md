# M5 — React frontend

## Role

Act as Project Manager/Supervisor. Delegate UI components and API client work with clear ownership. Do not allow frontend agents to change backend event contracts without supervisor approval.

## Objective

Build a responsive browser application that collects trip requirements and displays streamed planning progress, flight options, weather, places, routes and itinerary content.

## Required screens/components

- Landing/trip request screen.
- Trip input form: origin, destination, departure/return dates or duration, passenger count, budget, currency, interests, pace and constraints.
- Clear validation and missing-information prompts.
- Planning progress panel showing observable tool statuses.
- Flight results cards with airline, segments, dates/times, stops, price, currency, provider source and retrieval time.
- Weather summary with forecast dates, units and Open-Meteo attribution.
- Itinerary grouped by day, with activities, place details, estimated duration and route context.
- Map with itinerary markers and routes when valid coordinates/route data are available.
- Error, empty, loading, cancellation and partial-result states.
- Responsive desktop and mobile layouts.
- Accessibility: semantic controls, keyboard navigation, labels, contrast and live-region announcements for streaming status.

## Streaming client

- Use `fetch()` and `ReadableStream` to consume the POST SSE response from M4.
- Parse SSE framing correctly, including multi-line data, comments/heartbeats, chunk boundaries and terminal events.
- Handle cancellation with `AbortController`.
- Recover gracefully from network failure; do not automatically restart expensive LLM/API work without user consent.
- Render text safely; never inject model output as HTML.
- Validate event payloads at runtime.

## Map rendering

- Use the map provider and rendering approach selected in M0/M2.
- Render only coordinates returned by trusted provider adapters or validated domain data.
- Do not invent pins or route geometry.
- Include attribution and comply with map provider terms.
- Avoid exposing server-side API keys in the browser.

## Quality

- Use shared TypeScript contracts where practical.
- Add component tests for forms, streamed events, error states and itinerary rendering.
- Add browser-level smoke tests for the primary user journey.
- Provide useful empty states and clear data freshness labels.

## Delegation

- Frontend agent: page layout, trip form and itinerary components.
- Streaming agent: SSE client and progress UI.
- Map agent: map component and attribution.
- QA agent: accessibility and UI tests.
- Supervisor: design consistency, contract compatibility and integration.

## Acceptance criteria

- [ ] User can submit a valid trip request.
- [ ] Validation errors are understandable.
- [ ] Streaming progress and itinerary content render incrementally.
- [ ] Flight, weather and place data show sources/freshness.
- [ ] Map uses real returned coordinates and route data.
- [ ] Cancellation and failure states work.
- [ ] No secret keys are exposed in frontend bundles.
- [ ] Core UI is responsive and keyboard-accessible.
- [ ] Tests and production build pass.
- [ ] Human approves before M6.
